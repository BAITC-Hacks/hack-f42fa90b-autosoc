# Архитектура

## Статус

Backend, статический сайт, необязательный выбор цитат и диалоговый помощник на OpenAI Responses API реализованы. Без ключа форма подбора и её шаблонные объяснения работают; агент сообщает о недоступности.

## Компоненты

Приложение построено на Python и FastAPI. Тот же сервер отдаёт статический сайт на HTML, CSS и JavaScript без сборщика и отдельного frontend-сервера.

Backend разделяется на модули с одной ответственностью:

- `data` — чтение исходного CSV в UTF-8-SIG через `csv.DictReader` без его изменения, проверка схемы и явное отклонение HTML-страницы ошибки скачивания;
- `schemas` — схемы запросов, ответов и профилей, включая признаки происхождения данных;
- `matcher` — детерминированная фильтрация, различение пустых исходов и ранжирование;
- `explain` — построение кратких шаблонных объяснений из подтверждённых фильтрацией полей и атрибутированных фрагментов исходного описания;
- `config` — настройки из окружения и локального `.env`, без передачи ключа клиенту;
- `ai_explain` — один ограниченный по времени запрос модели для уже выбранных карточек, проверка идентификаторов полных серверных фрагментов собственных описаний и возврат к шаблону при ошибке;
- `agent` — ограниченный по времени диалоговый ход через Responses API с function calling; выбор инструмента делает модель, аргументы валидирует сервер, поиск выполняет существующий `matcher`.

Код проверяет ограничения, исключает занятых и ранжирует кандидатов. Из каждого `description` сервер выделяет полные фрагменты с идентификаторами; AI может выбрать только идентификатор фрагмента уже выбранного профиля. Код проверяет длину и содержательность подготовленных фрагментов и принадлежность выбранного идентификатора профилю, затем берёт исходный текст и собирает объяснение с атрибуцией. Неверный или неполный ответ, отказ и таймаут приводят к шаблонному объяснению. Этап выбора цитат не меняет параметры запроса, порядок и подтверждённые факты. Структурированный ответ реализован через официальный Python SDK и Responses API по [документации OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs); соответствие схеме не считается проверкой содержания.

## Реализованный HTTP API

Сайт доступен по `GET /`; каталог `static/` отдаётся по `/static/`. JavaScript получает значения формы из `GET /api/options` и отправляет запросы в `POST /api/match`, не повторяя правила подбора.

### `GET /health`

Проверка готовности процесса обслуживать запросы. Не должна раскрывать конфигурацию или секреты.

### `GET /api/options`

Возвращает доступные значения для формы (например, города, форматы и категории), полученные из фактически загруженных данных.

### `POST /api/match`

Принимает параметры подбора, валидирует их и возвращает один из трёх исходов, до трёх упорядоченных карточек, объяснения, сведения о неполной выдаче и статус известности доступности.

Точные JSON-схемы заданы в `app/schemas.py`; проверка входа и отрицательные сценарии покрыты тестами.

### `POST /api/agent`

Принимает сообщение пользователя и необязательный идентификатор сессии. Возвращает идентификатор, статус, короткий ответ, распознанные параметры, метку участия модели и имя выполненного инструмента. После поиска поле `match` содержит исходный `MatchResponse` со всеми карточками и причинами отсева. Текст о результате формирует сервер. Помощник доступен только при настроенном AI-ключе и режиме `auto`; иначе отвечает о недоступности и предлагает ручную форму. Повторный запрос с тем же идентификатором использует сохранённые параметры, а «Новый запрос» начинает новый диалог.

## Поток запроса

1. `schemas` валидирует входные параметры.
2. `data` предоставляет неизменённые исходные сведения и нормализованное представление.
3. `matcher` устанавливает наличие категории в городе, применяет ограничения и формирует детерминированный рейтинг.
4. `explain` создаёт шаблонные объяснения с собственным фрагментом описания.
5. При локальной настройке `ai_explain` за один запрос предлагает идентификаторы фрагментов для максимум трёх карточек. После проверки код пересобирает только объяснения и маркирует источник выбора фрагмента.
6. API возвращает структурированный ответ статическому сайту или другому HTTP-клиенту.

Для диалогового маршрута сервер отправляет модели компактный справочник значений из каталога и календарное окно. Модель выбирает `request_clarification` при неполных данных или `match_contractors` при полном запросе. Строгая схема инструмента включает изменённые поля и фрагменты последнего сообщения, на которых основано каждое изменение. Сервер проверяет аргументы через Pydantic, наличие фрагмента в сообщении и совместимость значения с фрагментом; неподтверждённое изменение ведёт к уточнению. Затем код вызывает тот же `matcher`; его результат остаётся авторитетным для карточек, цен, порядка, числа совпадений и причин. До двух обращений к модели нужны для выбора действия и краткой обработки результата поиска. Выбор фрагментов объяснения для агентского маршрута встроен во второй шаг, без вложенного вызова `/api/match`. Если поиск уже выполнен, а второй вызов не удался, сервер возвращает результат подбора с шаблонными объяснениями.

## Хранение и безопасность

На первом этапе не добавляются база данных, регистрация и бронирование. Исходный датасет остаётся неизменным. Ключ читается только на сервере из окружения или игнорируемого Git локального `.env`, причём окружение имеет приоритет. В браузер, ответ API и логи ключ не передаётся. Без ключа, а также в режиме `template`, внешний запрос не выполняется. Вызов SDK асинхронный, без автоматических повторов. Отдельный выбор цитат в `/api/match` ограничен примерно 7 секундами, весь агентский ход — примерно 9 секундами. Агентский контекст хранится в памяти процесса без БД: максимум 128 сессий, 12 сообщений на сессию, длина сообщения до 700 символов, срок неактивности 30 минут. Сообщения пользователя и описания считаются недоверенными данными, а роль `system`/`developer` или результат инструмента нельзя задавать через пользовательский ввод.

Архитектура должна обеспечивать чистый запуск по README без личного аккаунта участника. Сторонние компоненты и их назначение необходимо раскрывать в документации по мере фактического добавления.
