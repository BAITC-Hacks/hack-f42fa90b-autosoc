# Архитектура

## Статус

Backend, статический сайт и необязательный проверяемый этап выбора цитат через OpenAI Responses API реализованы. Без ключа объяснения создаются шаблоном.

## Компоненты

Приложение построено на Python и FastAPI. Тот же сервер отдаёт статический сайт на HTML, CSS и JavaScript без сборщика и отдельного frontend-сервера.

Backend разделяется на модули с одной ответственностью:

- `data` — чтение исходного CSV в UTF-8-SIG через `csv.DictReader` без его изменения, проверка схемы и доступ к профилям;
- `schemas` — схемы запросов, ответов и профилей, включая признаки происхождения данных;
- `matcher` — детерминированная фильтрация, различение пустых исходов и ранжирование;
- `explain` — построение кратких шаблонных объяснений из подтверждённых фильтрацией полей и атрибутированных фрагментов исходного описания.
- `config` — настройки из окружения и локального `.env`, без передачи ключа клиенту;
- `ai_explain` — один ограниченный по времени запрос модели для уже выбранных карточек, проверка цитат по их исходным описаниям и возврат к шаблону при ошибке.

Код проверяет ограничения, исключает занятых и ранжирует кандидатов. AI выбирает только точную цитату из `description` уже выбранного профиля. Код проверяет её длину, содержательность, соответствие id и точное вхождение в собственное описание, затем собирает текст с атрибуцией. Неверный или неполный ответ, отказ и таймаут приводят к шаблонному объяснению. AI не меняет фильтры, порядок и подтверждённые факты. Структурированный ответ реализован через официальный Python SDK и Responses API по [документации OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs); соответствие схеме не считается проверкой содержания.

## Реализованный HTTP API

Сайт доступен по `GET /`; каталог `static/` отдаётся по `/static/`. JavaScript получает значения формы из `GET /api/options` и отправляет запросы в `POST /api/match`, не повторяя правила подбора.

### `GET /health`

Проверка готовности процесса обслуживать запросы. Не должна раскрывать конфигурацию или секреты.

### `GET /api/options`

Возвращает доступные значения для формы (например, города, форматы и категории), полученные из фактически загруженных данных.

### `POST /api/match`

Принимает параметры подбора, валидирует их и возвращает один из трёх исходов, до трёх упорядоченных карточек, объяснения, сведения о неполной выдаче и статус известности доступности.

Точные JSON-схемы заданы в `app/schemas.py`; проверка входа и отрицательные сценарии покрыты тестами.

## Поток запроса

1. `schemas` валидирует входные параметры.
2. `data` предоставляет неизменённые исходные сведения и нормализованное представление.
3. `matcher` устанавливает наличие категории в городе, применяет ограничения и формирует детерминированный рейтинг.
4. `explain` создаёт шаблонные объяснения с собственным фрагментом описания.
5. При локальной настройке `ai_explain` за один запрос предлагает фрагменты для максимум трёх карточек. После проверки код пересобирает только объяснения и маркирует источник выбора фрагмента.
6. API возвращает структурированный ответ статическому сайту или другому HTTP-клиенту.

## Хранение и безопасность

На первом этапе не добавляются база данных, регистрация и бронирование. Исходный датасет остаётся неизменным. Ключ читается только на сервере из окружения или игнорируемого Git локального `.env`, причём окружение имеет приоритет. В браузер, ответ API и логи ключ не передаётся. Без ключа, а также в режиме `template`, внешний запрос не выполняется. Вызов SDK асинхронный, без автоматических повторов, с общим пределом примерно 7 секунд; кэш не применяется.

Архитектура должна обеспечивать чистый запуск по README без личного аккаунта участника. Сторонние компоненты и их назначение необходимо раскрывать в документации по мере фактического добавления.
